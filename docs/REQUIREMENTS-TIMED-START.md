# 需求草案：定时启动与额度窗口衔接

文档版本：v1.1；日期：2026-10-28。基于当前 0.4.0 功能。定时计划、持久化、调度和客户端入口已实现，见[实施与使用说明](TIMED-PLANS.md)；真实窗口启动规律及原生休眠／恢复仍待单独验证。本次不更改程序版本，未启用或执行用户的真实计划。

## 1. 用户目标

用户可以提前选择一个任务，在指定时间由客户端自动尝试执行。进一步提供时间规划：在用户开始工作前执行一次已授权的小任务，尽量让服务端确认的额度重置边界落在用户开始工作一段时间之后，从而先使用当前窗口的剩余额度，再衔接下一窗口。

用户希望达成的是：**醒来时仍有足够可用额度，在预计用完第一段额度附近迎来下一次自然重置，减少中间等待。** 额度是否充足、何时真正重置，始终以服务端实时数据为准。

### 1.1 用户示例

假设用户计划 08:00 开始使用，估计约两小时会用完一段额度；目标账户本次窗口长度为五小时，并且已经验证一次请求能够在适用条件下开启该窗口：

| 时间 | 期望安排 | 必须区分的事实 |
| --- | --- | --- |
| 05:00 | 自动执行用户选择的预触发任务 | 这是一次真实执行，会消耗额度；发送成功不等于窗口已经按预期建立 |
| 执行后 | 完整查询额度，核对服务端重置时间是否接近 10:00 | 记录实际返回值；不符合时显示偏差，不能自行改成 10:00 |
| 08:00 | 用户开始使用当前窗口的剩余额度 | 完整查询剩余比例与周额度，核对是否达到用户设置的“充足”目标 |
| 10:00 附近 | 服务端确认自然重置后使用下一窗口 | 到达本地时间本身不是重置证据，仍需新鲜完整查询 |

预期是让用户在约四小时的工作区间中跨过一次重置边界。两小时是用户的使用估计，不代表系统能够保证两小时恰好耗尽，或保证持续工作时长。

## 2. 能力依据与可行性边界

截至本次核对，官方资料描述了适用套餐的五小时用量，以及可能存在的周额度；实际消耗随模型、任务复杂度等变化。当前额度与重置时间应查看实际用量数据。[官方用量说明](https://learn.chatgpt.com/docs/pricing)

App Server 的额度读取返回窗口长度 `windowDurationMins` 和下一次重置时间 `resetsAt`，应用应使用这些服务端字段。[官方 App Server 额度接口](https://learn.chatgpt.com/docs/app-server)

上述资料不足以确认所有账户都遵循“空闲后的首次请求启动新的五小时倒计时”。因此：

1. **指定时间执行任务**可以作为独立功能开发，不依赖这个假设。
2. **提前执行并衔接窗口**属于条件性规划。开发前需核对本机 CLI、当前账户、完整额度数据及实际窗口行为；未经确认时标为实验估算。
3. 已存在的窗口、滚动规则、其他客户端的使用和服务端调整，都可能使预期时间不成立；不能通过发送一次请求随意改变已有重置时间。
4. 工具可以编排自身任务时间，不能预先保证某个时刻获得完整额度，也不能保证持续使用两份完整额度。
5. 查询本身、打开客户端、保存日程均不能被当成已经启动额度倒计时的证据。

本期仅编排自然额度窗口下的任务。付费额度购买、额外重置能力及账户切换不纳入本需求。

## 3. 首期范围

| 编号 | 能力 | 首期要求 |
| --- | --- | --- |
| T01 | 指定时间启动 | 选择已有任务及版本，在指定日期、时间尝试启动 |
| T02 | 重复计划 | 支持单次和每日；按周、复杂日历、cron 表达式留待后续 |
| T03 | 窗口衔接助手 | 根据开始使用时间、预计首段使用时长和服务端窗口长度计算提前执行时间，显示适用条件及偏差 |
| T04 | 预留时段 | 在确认的时段内，限制本工具派发其他自动任务，减少与用户争用额度 |
| T05 | 到时校验 | 仍须通过真实额度、账户、权限、目录、模型、执行权及派发状态校验 |
| T06 | 错过与阻塞处理 | 明确区分未到时间、等待执行权、等待额度、派发暂停、已错过和待人工核对 |
| T07 | 管理及通知 | 查看、编辑、启用、暂停、取消计划，展示时间线及安全诊断 |
| T08 | 持久化及恢复 | 计划、触发实例、运行快照和去重证据持久化，重启不重复发送 |

首期继续采用当前本地后台：电脑需要开机、后台存活且可连接 Codex。隐藏到托盘可继续运行；退出客户端、关机、休眠或网络不可用时不能保证按时执行。系统自动唤醒、开机启动、安装系统服务和云端代执行留待独立需求。

## 4. 两种操作模式

### 4.1 指定时间执行

用户选择已有任务，核对不可变版本、会话、模型及权限，设置时间后预览并明确启用。到时发起执行前校验；满足所有条件才发送指令。

时间表示“最早允许启动”，不是承诺远端恰好在该秒开始。界面精度到分钟；无阻塞时，在到时后的一个调度周期内开始预检。调度周期、网络及服务端响应产生的延迟需有观测记录。

### 4.2 窗口衔接助手

用户提供：

- 计划开始使用时间 `S`，例如 08:00；
- 希望在开始使用多久后衔接下一窗口 `L`，例如 120 分钟；
- 当前账户服务端返回的目标窗口长度 `D`，例如 300 分钟；
- 预触发任务及版本；
- 开始使用时希望保留的最低额度比例，以及保护截止时间。

计算关系：

```text
目标重置时间 R = S + L
估算提前执行时间 A = R - D = S - (D - L)

示例：08:00 + 2 小时 - 5 小时 = 05:00
即：提前 3 小时执行一次预触发任务，期望在 10:00 附近重置。
```

规则：

1. `D` 来自用户明确选择的额度窗口，不在代码中固定为五小时；无法取得可信长度时只能创建普通定时计划，不能宣称完成衔接计算。
2. `L` 是预计使用时长，要求大于 0 且小于 `D`；不符合时解释原因，不静默更改用户输入。
3. `A`、`S`、`R` 分开显示。跨午夜时 `A` 可以在前一天，计划按目标使用日期标识。
4. 目标是“开始工作一段时间后重置”。若用户希望“醒来前已经重置”，应将目标 `R` 设在 `S` 或更早，并重新计算，不能同时把当前窗口称为刚重置和即将重置。
5. 已有服务端重置时间时优先展示该事实。若与目标不符，提示采用现有边界、调整计划或改为普通定时执行；不重复发送请求来尝试强制对齐。
6. 尚不能确认窗口启动规则时，明确显示“实验估算”。只有用户单独确认可能消耗额度及对齐失败风险后，才允许按估算时间尝试一次；额度或权限数据本身未知时仍阻断。
7. 预触发只发送已确认的任务快照，不自动编造提示词、反复发消息或把同一任务重新发送至另一会话。建议由用户选择独立、短小、低影响的任务。
8. 保存计划和到达时间都不能显示“已启动倒计时”。执行后须重新完整查询，分别记录目标和实际重置时间。
9. 不自动在 `S` 再执行一条业务指令。用户需要时，可另行明确选择并授权该阶段；仅提醒开始使用不包含任务发送授权。

## 5. “醒来有足够额度”的可验证目标

“充足”定义为用户设置的目标比例，例如开始使用时希望目标窗口剩余不少于 90%；该值是计划目标，不是工具可强制实现的结果。周额度和其他相关窗口还必须满足现有有效保留线。

在 `S` 附近完整查询后，展示“已达到目标”“未达到目标”或“数据未知”，附观测时间。低于目标时通知用户，不虚报可用，也不通过改低保留线消除提示。

提前任务会消耗当前窗口；其他设备、官方客户端、其他后台实例和用户手动任务也可能消耗同一账户额度。功能只能管理其自身服务的派发，不能独占整个账户额度。

## 6. 预留时段及执行冲突

1. 窗口衔接计划默认提供可见的“保护额度时段”，由用户确认开始、结束时间。示例可为 05:00 至 12:00，覆盖预触发、08:00 开始使用及 10:00 后的第二段使用。
2. 保护期内，同一受管数据库服务、同一账户来源的普通自动任务及额度中断续接等待派发；本次明确授权的预触发实例可以执行。其他计划只有被单独明确纳入允许范围才可执行，不能仅凭相同任务 ID 获得豁免。
3. 用户通过本工具手动执行时，应提示该操作会影响预留额度，明确确认后仍遵循原有权限和执行校验；本功能不拦截官方客户端或其他数据库实例。
4. 保护不强行终止已经运行的任务。计划预览须提示当前执行冲突，以及未知运行时长可能带来的延迟。
5. 保护到期只移除该计划自己的时段限制，不解除用户手动暂停、不撤销待核对阻塞，也不自动启动已停止的服务。
6. 多个保护时段可以叠加。相互冲突的预触发计划必须在启用前提示，并由用户调整，不静默覆盖另一计划。
7. 预触发任务沿用其明确的执行超时。最晚启动时间与最长运行时间分别展示；任务开始后可能跨过用户开始使用时间，不能将“已请求取消”当作已终止。
8. 暂停或取消计划时，明确提示并撤销该计划自己的保护限制；其他计划的保护、用户手动暂停和待核对阻塞保持不变，不能残留没有可管理来源的限制。

## 7. 与现有队列的关系

定时计划有独立的“到时”触发条件；普通队列继续使用现有 available／refresh 规则。定时实例不额外等待普通队列的下一次刷新事件，也不消耗普通 refresh 队列的单次触发凭据。

所有来源共用现有执行权、真实额度、权限与全局派发开关。到时且符合条件的记录进入相同的候选排序；按快照优先级及稳定顺序领取，不抢占活动执行。到时不会跳过其他安全校验。

保存草稿不授权执行。“启用计划”须明确确认任务版本、重复频率、时间和无人值守执行范围。若派发仍暂停或服务未运行，界面必须醒目说明：**计划已启用，但当前不会执行**；不得因保存或启用而偷偷恢复派发。

任务编辑、停用或归档：

- 计划绑定确认时的版本；编辑任务不自动换用新指令、会话、模型或权限。
- 采用新版本需重新预览并确认；既有运行快照保持不变。
- 当前任务停用或归档时不再派发该计划，显示对应原因。
- 计划的暂停或取消影响未来及未领取实例；活动运行需单独请求取消，并等待准确终态。

## 8. 时间、错过执行及重复规则

| 项目 | 需求 |
| --- | --- |
| 时区 | 显示并保存 IANA 时区，例如 Asia/Shanghai；执行时刻保存 UTC，同时保留原始当地时间与时区用于解释 |
| 每日计划 | 按计划时区的当地日期生成下一实例，不简单给 UTC 时间加 24 小时 |
| 夏令时 | 不存在的当地时间跳过并说明；重复出现的当地时间仅生成一次，预览明确选用的 UTC 偏移 |
| 系统时区更改 | 不改变已保存的计划时区；用户修改计划时区须重新预览并确认 |
| 时钟跳变 | 检测明显向前／向后跳变后停止新定时派发，提示校时和重新核对；不能重复触发或以时间跳变认定额度恢复 |
| 最早执行 | 任何路径都不得早于 `dueAt` 发送任务；提前只读准备信息不构成执行 |
| 最晚启动 | 需设置启动有效期。草案建议默认到时后 5 分钟，用户可在实现规定范围内调整；过期未启动则记为已错过 |
| 电脑／服务未运行 | 默认跳过已错过实例；可由用户在启用时单独允许有效期内补执行一次，不追赶全部历史日期 |
| 过去时间 | 新建单次计划不能静默把过去时间改成立即执行；选择未来时间，或使用现有手动执行入口 |
| 客户端重启 | 保留计划定义与实例记录，但沿用启动暂停和遗留执行权检查；需显式恢复派发，不重发已领取记录 |

上述有效期只决定能否开始，不作为已启动运行的结束证明。公式中的分钟时长按真实经过时间计算；先把目标当地时间解析为 UTC 时刻，再计算 `A` 和 `R`，避免跨日或夏令时误差。

## 9. 状态及反馈

计划状态与运行结果分开保存，不能用一个“已启用”代表一定执行成功。

| 类别 | 状态示例 | 含义 |
| --- | --- | --- |
| 计划定义 | 草稿、已启用、已暂停、已取消、已结束 | 用户授权和未来生成规则 |
| 单次实例 | 未到时间、到时待派发、等待额度、等待执行权、受时段保护、已错过 | 尚未开始实际执行的原因 |
| 执行结果 | 运行中、成功、失败、待人工核对、已取消 | 关联现有运行记录与准确回合证据 |
| 衔接评估 | 仅估算、已取得服务端时间、与目标相符、与目标不符、未知 | 只描述实际观测，不代替运行成功或额度可用 |

重点提示包括：派发暂停、账号变化、授权失效、预触发未执行、启动延迟、实际重置偏离目标、开始使用时未达额度目标，以及需要人工核对。通知使用概括文字，不暴露指令、凭据、邮箱或私人目录。

## 10. 客户端界面

新增“定时计划”入口，提供计划列表及创建／编辑页面。

### 创建流程

1. 选择“指定时间执行”或“窗口衔接助手”。
2. 从现有任务名称下拉中选择任务，展示版本、目标会话、模型和权限摘要。
3. 设置单次／每日、日期、时间和时区。衔接模式额外填写开始使用时间、预计首段时长及剩余额度目标，并选择预触发任务。
4. 查看估算时间线、最新服务端边界、保护时段、可能冲突和最晚启动时间。
5. 选择“保存草稿”或明确“启用计划”；默认不勾选无人值守执行授权。

列表展示：计划名称、任务及版本、模式、下次执行时间、目标使用时间、实际重置时间、派发状态、保护状态和最近结果。支持查看详情、编辑、启用／暂停、取消未来安排及查看关联运行；正常操作不要求手填计划 ID、任务 ID 或会话 ID。

窗口衔接详情必须同时展示以下三类信息，名称不能混用：

- **计划**：预计 05:00 执行，08:00 开始使用，目标 10:00 重置；
- **事实**：实际执行时间、服务端最近返回的重置时间及额度比例；
- **评价**：是否符合目标、观测是否过期、哪些结果尚不能确认。

## 11. 持久化、去重及恢复

### 数据对象

| 对象 | 关键内容 |
| --- | --- |
| 定时计划 | 自动 ID、revision、名称、模式、账户／来源绑定、已确认任务版本、时区、单次／每日规则、开始及截止日期、启动有效期、错过策略、授权状态 |
| 衔接配置 | 目标使用时刻、预计首段时长、窗口选择及观测来源、目标重置时间、估算执行时间、额度目标和保护区间 |
| 触发实例 | 稳定实例 ID、目标使用日期、阶段、到时及截止 UTC、计划 revision 快照、领取／发送证据、关联运行 ID、状态及固定原因码 |
| 运行与观测 | 复用不可变任务快照、执行权、准确会话／回合、服务端额度检查点及安全审计事件 |

### 必须成立的约束

1. 现有普通入队的 `(taskId, revision)` 去重规则保持。每日计划需以明确授权的独立实例生成运行，不能因旧版本已经执行而永远返回第一天的记录。
2. 实例有稳定逻辑标识，计划 ID、目标使用日期和阶段参与生成；计划 revision 用于并发检查和审计，不能靠改 revision、时区或执行时间再次发送同一已触发实例。跨夏令时和跨午夜均只生成应有次数。
   同日实例已触发后，修改当天执行时间不再自动执行一次；确需另一次执行时，应使用独立计划或手动入口重新明确授权。
3. 编辑计划时事务内处理未领取实例；已经领取、已提交或结果不明的实例保留，不能自动以新版本覆盖或重建。
4. 到时资格重验、实例消费、运行关联及执行权领取按现有同步 SQLite 事务规则原子保存。多次扫描、两个客户端、重复通知和重启不能创建重复自动提交。
5. 只读查询可以按规则重试；明确尚未发送的预检等待可以继续核查。同一实例的自动发送尝试至多一次，提交结果不明时保持 `needs_attention`，不承诺网络层恰好一次成功。
6. 崩溃后已领取记录不得自动释放或重发；恢复仅查询已记录来源和准确回合，不猜测最新聊天，也不把 resume/start 当成只读检查。
7. 取消或归档计划保留历史、去重标识和已发生结果；移除待核对队列记录不使计划实例重新变成可发送。
8. 账户、来源或授权环境变化时停止相关派发并要求重新核对，不自动切换账户或放宽权限。迁移保留已有 0.4.0 任务、运行、队列和备份数据。

## 12. 诊断和安全边界

沿用现有回环地址、会话／CSRF、固定 IPC、真实额度检查、全局互斥、人工审批及取消终态规则。模拟模式只预览和验证状态，不发送真实任务。

记录计划／实例 ID、计划与实际时间、时区、调度延迟、固定等待原因、额度观测来源、窗口长度、目标与实际重置偏差及发送证据。导出重新进行字段白名单投影；不记录原始 RPC 错误、凭据、任务指令或完整私人路径。

首次真实验证先做只读版本和协议核对。需要验证窗口启动行为时，另行针对明确账户、独立任务和消费范围取得授权；不为验收故意耗尽额度，不恢复或重发用户原任务。

## 13. 验收清单

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| TS01 | 保存草稿或创建计划 | 无真实发送，默认未启用；自动生成 ID |
| TS02 | 定时尚未到达 | 所有入口均不提前提交 |
| TS03 | 到时且额度、权限及执行权可用 | 使用确认版本，在一个调度周期内开始预检，最多一次自动发送尝试 |
| TS04 | 派发暂停／服务停止 | 显示阻塞原因，不自动恢复派发或启动服务 |
| TS05 | 额度耗尽、低于任一保留线、缺失或过期 | 等待或过期跳过，不把未知当作恢复 |
| TS06 | 普通模式为 refresh，定时实例到时 | 按独立时间条件核验，不消费普通刷新凭据，仍共享所有安全校验 |
| TS07 | 当前任务执行中或高优先级候选在前 | 不抢占，显示延迟；超过启动有效期不再补发 |
| TS08 | 08:00、预计两小时、服务端窗口 300 分钟 | 估算 05:00 执行、目标 10:00 重置，并标明条件 |
| TS09 | 服务端窗口不是五小时或长度未知 | 按实际长度计算，或禁用衔接计算；不固定 300 分钟 |
| TS10 | 已有窗口与目标重置不符 | 展示真实边界和偏差，不重复发送以强制对齐 |
| TS11 | 请求成功但重置信息未变化／未返回 | 不显示已按计划启动新窗口，状态保持不符或未知 |
| TS12 | 到达目标重置时间但尚无新鲜完整查询 | 不认定额度恢复，不启动依赖新窗口的任务 |
| TS13 | 预留时段内普通自动任务及续接 | 等待保护解除；仅明确允许的实例可执行 |
| TS14 | 保护到期而用户暂停或存在待核对记录 | 只解除本计划保护，其他阻塞继续有效 |
| TS15 | 其他客户端消耗、周额度不足、08:00 低于目标 | 显示未达目标或未知，不保证剩余额度或连续工作时长 |
| TS16 | 每日同一任务版本执行、多次扫描和并发客户端 | 每个授权日期有独立实例，同一实例不重复发送 |
| TS17 | 执行后编辑时间／时区／任务版本 | 不重建或重发已触发实例，新版本需重新确认 |
| TS18 | 休眠、断网、后台未运行及错过多日 | 默认跳过；允许补执行时仅在有效期内补一次，不集中补发历史 |
| TS19 | 跨午夜、夏令时缺失／重复时间、系统时区改变 | 日期归属、UTC 时刻及实例次数正确，选择依据可解释 |
| TS20 | 系统时钟前跳／后退、进程崩溃 | 暂停新触发并保留执行权证据，不因本地时间认定恢复或重复提交 |
| TS21 | 提交确认丢失、审批或输入请求 | 待人工核对，不自动批准或重发 |
| TS22 | 停用／归档任务、取消计划、活动运行取消 | 停止未来派发，历史保留；活动取消等待准确终态 |
| TS23 | 普通入队去重、旧备份导入及模式升级 | 保留既有语义和数据，不清库或改写历史快照 |
| TS24 | 通知、错误日志及诊断导出 | 时间与原因足够排查；无凭据、原始错误、指令和完整私人路径 |
| TS25 | mock、demo、预览及本地验收 | 仅模拟，不创建真实发送或实际定时任务 |

关键时间、额度和调度逻辑必须使用可注入时钟、模拟快照及协议替身验证。原生休眠／恢复和真实窗口行为另行记录，不用模拟结果替代。

## 14. 首期实现约定

- 计划时区使用 IANA 标识；启动有效期为 1–1440 分钟，默认 5 分钟；每日结束日期可选。最多保存 1000 个计划，历史不自动清空。
- 预览最多显示近期三个 UTC／本地时间线；夏令时不存在的当地时刻跳过并留存一次通知标记，重复时刻取首次。历史实例 ID 跨编辑、取消和重启保留。
- 衔接长度仅采用完整查询返回的所选窗口；`0 < L < D`，开始使用后的保护分钟数至少覆盖 L。自相重叠的每日保护与其他计划保护冲突均要求调整，不静默授权其他实例。
- 完整可用额度首次未报告重置时间时，可在单独确认实验和保护风险后尝试一次；已有历史边界丢失、额度缺失、过期或未知仍阻断。已有服务端边界与目标相差超过一分钟时等待调整，不尝试强制对齐。一分钟仅用于规划偏差显示，不参与额度刷新识别。
- 派发模式 refresh 的普通队列凭据与定时触发分开；同一实例一旦有发送证据便不再自动尝试。额度中断续接仍须任务原有显式授权、准确耗尽／重置证据，并遵守保护时段。
- 到开始使用时间 S 后，在启动有效期对应的观测容差内以首次完整读数评估目标；未获得读数则记未知。活动执行、离线或查询退避可能延迟观测，不补造准时证据。
- 保护只约束同一数据库服务及绑定来源；手动执行须确认本次覆盖，CLI 对应 `--allow-protected`。暂停／取消只撤销自身保护，不解除全局暂停或其他人工核对。
- 当前没有系统自动唤醒、系统服务、开机启动、云端执行或保证两份完整额度的能力。真实端到端执行与稳定版人工验收没有由隔离测试替代。

## 14. 建议开发顺序

1. 定时领域模型、时区计算、单次／每日实例生成及纯逻辑测试。
2. 持久化迁移、并发 revision、稳定实例去重和与执行权的事务集成。
3. 指定时间触发、有效期、阻塞原因、错过执行及重启恢复。
4. 定时计划 GUI 和通知，先交付可独立使用的普通定时执行。
5. 服务端窗口行为核实、衔接助手、预留时段和目标观测；能力不足时保持实验或只提供计划计算。
6. 完整模拟／打包验收，之后按单独授权完成真实小任务及原生休眠／恢复验收。

领域模型与时间规则放在 `src/domain`，外部协议放在 `src/adapters`，调度器仅依赖领域接口。此处是后续实现的分块建议，不代表功能已经开发完成。
