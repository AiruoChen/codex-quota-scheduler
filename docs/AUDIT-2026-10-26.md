## 已确认的问题

### A1 / P1：执行前检查没有继承已知额度窗口约束

位置：[codex-executor.ts:27](../src/adapters/codex/codex-executor.ts#L27)，对照 [recognize.ts](../src/monitor/recognize.ts) 与 [manual-service.ts](../src/executor/manual-service.ts)。

触发条件：监控已经观察到五小时及周窗口，之后周窗口从查询响应中消失。监控仓储正确保留已知窗口，并判定 `unknown / missing_window`；手动执行却只把本次查询的窗口传给 `evaluateQueue`，没有读入已知窗口约束。

复现：先记录周额度耗尽的双窗口快照，再记录仅剩 primary 的快照，随后用返回相同账户及仅 primary 的协议替身执行手动任务。结果：

```json
{"monitorState":{"status":"unknown","reason":"missing_window"},"status":"succeeded","submissions":1}
```

影响：管理界面可以显示“额度未知”，同时手动入口仍提交任务，违反 F03/F07、D03/D07 及“缺失窗口表示未知”的约束。自动领取后的执行预检也只接收 `expectedAccount`，没有传递预期窗口集合，静态审查显示它存在同类信息丢失风险；本次动态反例覆盖的是手动路径。

建议：让手动和自动执行共用包含来源、身份、已知窗口集合及新鲜度的领域预检。完整查询缺少已知窗口时返回等待，不得用另一个只看当前窗口的判断覆盖 `missing_window`。新增“监控未知而手动执行”的反例，以及领取后查询丢失周窗口的自动路径测试。

### A2 / P1：账户对象存在即可放行，未要求可验证的账户标识

位置：[codex-executor.ts:30](../src/adapters/codex/codex-executor.ts#L30)，对照 [session.ts](../src/adapters/codex/session.ts)、[scheduler-repository.ts](../src/storage/scheduler-repository.ts) 及 [recovery-reader.ts](../src/adapters/codex/recovery-reader.ts)。

触发条件：服务端返回 `type: chatgpt`，但 `email` 和 `workspaceId` 均为 `null`。`readAccount` 返回非空对象；执行器仅检查 `!quota.account`。前后两次读取到相同的空标识对象，也会通过对象相等检查。

复现：协议替身返回上述账户，经过真实 `ManualExecutionService`、文件 SQLite、执行权及 `CodexExecutor` 路径，结果为：

```json
{"account":{"type":"chatgpt","email":null,"planType":"plus","workspaceId":null},"status":"succeeded","submissions":1}
```

影响：无法证明所用账户身份时仍能发送指令；此后恢复读取器反而会返回 `ACCOUNT_UNKNOWN`。自动调度和恢复已有非空身份检查，手动入口行为与之不一致。对应 F01/F07、D07 及未知身份不得派发的验收要求。

建议：提交前要求至少存在一个项目认可的稳定身份字段；将该校验放入共享领域预检。缺失身份时保持等待/明确失败且 `turn/start` 次数必须为零，并补充手动与自动路径反例。

### A3 / P1：会话准备后没有再次校验额度有效期

位置：[codex-executor.ts:54](../src/adapters/codex/codex-executor.ts#L54) 至调用 `runTurn` 的阶段；首次额度判断位于第 27 行。

触发条件：额度查询和首次判断之后，还要等待 `thread/read`、`thread/start` 或 `thread/resume`、`account/read`。这些等待可以跨过 `quotaMaxAgeMs` 或服务端窗口重置边界。最后仅复核账户和取消信号，没有重新检查先前快照的年龄/重置时间。

复现：使用可注入时钟，令 `quotaMaxAgeMs=1000`，在 `thread_ready` 后推进时钟 2000 ms。协议替身仍收到一次 `turn/start`，运行最终为 `succeeded`。

影响：已过期的额度快照仍能放行手动或自动提交，违反 F03/F07/F08、D07 及“过期表示未知”的要求。该反例模拟的是正常网络延迟造成的检查与使用间隔。

建议：在 `turn/start` 的最后一道提交边界复核身份、快照年龄和服务端窗口边界；若快照到期，则重新完整查询并应用 A1 的窗口规则。新增会话准备跨过最大年龄、跨过窗口边界和时钟回退的测试。

### A4 / P2：刚导入但尚未启动的活动配置可以绕过客户端降级保护

位置：[data-transfer.ts:238](../src/desktop/data-transfer.ts#L238)，关联 `selectedProfile`、`select` 和导入时写入的 `profile.json`。

触发条件：导入完成已经生成 `profile.json.clientVersion` 并切换活动指针，但尚未启动新副本，因此该配置没有 `data-versions` 记录。下一次启动读取活动指针后，`prepareStartup` 只核对后者，没有核对导入标记中的客户端版本。

复现：用版本参数 `9.9.9` 完成一次真实合成数据库导入，不调用 `opened()`；随后以 `0.3.0` 的版本参数对已选中的配置调用 `prepareStartup()`：

```json
{"importedClientVersion":"9.9.9","attemptedClientVersion":"0.3.0","openedAfterImport":false,"outcome":"accepted"}
```

影响：普通切换配置会拒绝的新版数据，在活动配置启动路径中可以被旧客户端打开并写入。数据库模式更高时仍有 schema 保护；缺陷发生在客户端版本更高而模式仍兼容的情况下。对应 D13/D14 和客户端/数据库版本分别管理的要求。

建议：把导入标记、已打开版本记录及数据库模式检查收敛到统一兼容性守卫，活动启动、显式切换和备份恢复均调用；所有检查应先于备份转换、暂停写入及服务启动。新增“导入后未启动即回退客户端”的测试。
